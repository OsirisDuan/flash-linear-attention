# Kernel 优先级评估框架

## 1. 框架概述

### 1.1 定义

Kernel 优先级评估框架（Kernel Priority Evaluation Framework，简称 KPEF）是一套面向 Triton kernel 函数的多维度量化评估体系，用于在 flash-linear-attention 等线性注意力代码仓库中，系统性地识别和排序高优先级 kernel，指导优化资源分配和测试覆盖策略。

### 1.2 目的

- **资源聚焦**：在有限的开发和测试资源下，优先保障对系统影响最大的 kernel
- **风险管控**：识别缺乏测试覆盖的高影响 kernel，降低生产环境故障风险
- **优化决策**：为 kernel 性能优化提供数据驱动的优先级依据
- **跨团队协作**：建立统一的评估标准，便于不同角色对优先级达成共识

### 1.3 适用范围

- flash-linear-attention 仓库中所有 `@triton.jit` 装饰的 kernel 函数
- 其他使用 Triton 实现算子的代码仓库（需调整维度权重）

## 2. 评估维度

### 2.1 维度总览

| 维度 | 权重 | 核心问题 |
|------|------|---------|
| 模型热度 | 35% | 该 kernel 被哪些模型使用？这些模型在业界的地位如何？ |
| 复用度 | 30% | 该 kernel 被多少个算子共享？修改它的影响范围有多大？ |
| 核心程度 | 20% | 该 kernel 在模型执行路径中处于什么位置？ |
| 测试缺失度 | 5% | 该 kernel 当前的测试覆盖情况如何？ |
| 技术复杂度 | 10% | 该 kernel 的实现复杂度和优化潜力如何？ |

### 2.2 维度一：模型热度（权重 35%）

**评估逻辑**：分析 kernel 所属算子被哪些模型使用，以及这些模型在业界的地位。

#### 模型热度分级标准

| 级别 | 标准 | 典型代表 | 得分 |
|------|------|---------|------|
| **S级** | 被知名大模型产品正式采用 | GDN → Qwen3-Next, KDA → Kimi, MLA → DeepSeek | 5 |
| **A级** | 发表在顶会（ICML/NeurIPS/ICLR/ACL）且有活跃官方仓库 | GLA, Mamba2, RetNet, DeltaNet, HGRN | 4 |
| **B级** | 有正式论文发表，但工业采用度有限 | RWKV6, HGRN2, GSA, Based, Rebased | 3 |
| **C级** | 预印本或新发表，社区验证尚不充分 | RWKV7, MesaNet, Comba, PaTH, MoM | 2 |
| **D级** | 实验性/探索性模型，无正式论文 | 部分内部实验模型 | 1 |

#### 模型热度得分计算

```
模型热度得分 = max(该 kernel 被使用的所有模型的热度级别得分)
```

**说明**：一个 kernel 可能被多个模型使用，取最高级别得分。因为高热度模型的存在已经足以提升该 kernel 的优先级。

### 2.3 维度二：复用度（权重 30%）

**评估逻辑**：分析 kernel 被多少个算子共享使用，复用度越高，修改影响范围越大。

#### 复用度分级标准

| 级别 | 标准 | 得分 |
|------|------|------|
| **极高** | ≥4 个算子共享 | 5 |
| **高** | 3 个算子共享 | 4 |
| **中** | 2 个算子共享 | 3 |
| **低** | 单一算子独占，但该算子被多个模型使用 | 2 |
| **极低** | 单一算子独占，且该算子仅被 1 个模型使用 | 1 |

#### 共享 Kernel 识别方法

1. **检查 `fla/ops/common/` 目录**：该目录下的 kernel 天然是多算子共享的
2. **追踪 import 链**：搜索 `from fla.ops.common` 引用，统计每个 kernel 被引用的次数
3. **检查算子间 import**：某些算子可能直接 import 其他算子的 kernel

#### 已识别的高复用 Kernel

| 共享 Kernel | 被使用的算子 | 复用度级别 |
|------------|-------------|-----------|
| `chunk_fwd_h` / `chunk_bwd_dh` (chunk_h) | GLA, SimpleGLA, GSA, RWKV6, MesaNet | 极高 |
| `chunk_fwd_o` / `chunk_bwd_dqkwg` / `chunk_bwd_dv` (chunk_o) | SimpleGLA, DeltaRule, GatedDeltaRule, Comba | 极高 |
| `fused_recurrent` | GLA, SimpleGLA, GSA | 高 |
| `chunk_gated_delta_rule_fwd_h` / `chunk_gated_delta_rule_bwd_dhu` (chunk_delta_h) | DeltaRule, GatedDeltaRule, KDA, Comba | 极高 |
| `chunk_scaled_dot_kkt_fwd` | DeltaRule, GatedDeltaProduct, PaTH | 高 |

### 2.4 维度三：核心程度（权重 20%）

**评估逻辑**：分析 kernel 在模型执行路径中的位置和重要性。

#### 核心程度分级标准

| 级别 | 标准 | 典型场景 | 得分 |
|------|------|---------|------|
| **核心** | 前向传播主计算路径 | attention 计算、状态更新、输出投影 | 5 |
| **重要** | 反向传播梯度计算路径 | 梯度累积、梯度分发 | 4 |
| **辅助** | 预处理/后处理步骤 | cumsum、mask 处理、数据重排 | 3 |
| **优化** | 性能优化专用 kernel | 融合操作、内存优化 | 2 |
| **边缘** | 可选或降级路径 | naive 实现、调试用 kernel | 1 |

#### 核心程度判断方法

1. **函数名分析**：
   - 含 `fwd` 且无 `intra`/`inter`/`preprocess` → 通常是核心前向 kernel
   - 含 `bwd` → 反向传播 kernel
   - 含 `cumsum`/`preprocess`/`mask` → 辅助 kernel
   - 含 `fused` → 优化 kernel

2. **调用链分析**：
   - 在 layer 的 `forward()` 方法中直接调用的 → 核心
   - 在 `backward()` 或梯度函数中调用的 → 重要
   - 在辅助函数中调用的 → 辅助

3. **计算量分析**：
   - 包含 `tl.dot()` 的 kernel → 计算密集，通常是核心
   - 纯向量操作 → 可能是辅助或优化

### 2.5 维度四：测试缺失度（权重 5%）

**评估逻辑**：当前测试覆盖越差，补充测试的优先级越高。

#### 测试缺失度分级标准

| 级别 | 标准 | 得分 |
|------|------|------|
| **严重缺失** | 无任何测试用例 | 5 |
| **明显不足** | 有测试但仅覆盖单一场景 | 4 |
| **部分覆盖** | 有基本功能测试，缺少边界/梯度测试 | 3 |
| **基本覆盖** | 有功能测试和梯度测试 | 2 |
| **充分覆盖** | 功能、梯度、边界、多数据类型全覆盖 | 1 |

#### 测试缺失度评估方法

1. **读取 `kernel_test_coverage.csv`** 中的"测试覆盖情况"列
2. **分析测试函数**：
   - 是否测试了前向正确性
   - 是否测试了梯度正确性（`torch.autograd.gradcheck` 或对比实现）
   - 是否测试了不同序列长度、head 维度
   - 是否测试了不同数据类型（fp32, bf16, fp16）

### 2.6 维度五：技术复杂度（权重 10%）

**评估逻辑**：复杂度越高，出 bug 的概率越大，优化潜力也越大。

#### 技术复杂度分级标准

| 级别 | 标准 | 得分 |
|------|------|------|
| **极高** | cv/cube 类型 + 函数体 >50 行 + 多个 `tl.dot()` 调用 | 5 |
| **高** | cv/cube 类型 + 函数体 >30 行 | 4 |
| **中** | cv/cube 类型 + 函数体 ≤30 行，或 vv 类型 + 函数体 >30 行 | 3 |
| **低** | vv 类型 + 函数体 15-30 行 | 2 |
| **极低** | vv 类型 + 函数体 <15 行 | 1 |

#### 技术复杂度评估方法

1. **kernel 类型**：从 CSV 的"kernel类型"列获取（`cv/cube` 或 `vv`）
2. **函数行数**：从源码统计函数体行数
3. **`tl.dot()` 调用次数**：统计函数中 `tl.dot()` 出现的次数

## 3. 实施方法

### 3.1 数据收集阶段

#### 步骤 1：建立算子-模型映射

1. 遍历 `fla/models/` 下每个模型目录
2. 读取 `modeling_*.py` 文件中的 import 语句
3. 提取 `from fla.layers.xxx import Yyy` 中的 layer 名称
4. 建立"模型 → layer → 算子"的映射关系

**关键文件**：
- `fla/models/*/modeling_*.py`：模型定义
- `fla/layers/*.py`：layer 定义，包含算子 import

#### 步骤 2：建立算子-Kernel 映射

1. 读取 `tmp/operators_kernels_mapping.csv` 获取算子与 kernel 的对应关系
2. 注意"映射关系类型"列：一对多表示一个算子对应多个 kernel

#### 步骤 3：建立 Kernel 复用度映射

1. 搜索 `from fla.ops.common` 的 import 语句
2. 统计每个共享 kernel 被引用的次数
3. 检查算子间的直接 import

#### 步骤 4：收集 Kernel 技术属性

1. 从 `tmp/operators_kernels_mapping.csv` 获取 kernel 类型和源码路径
2. 从源码统计函数行数和 `tl.dot()` 调用次数

#### 步骤 5：收集测试覆盖数据

1. 从 `tmp/kernel_test_coverage.csv` 获取测试覆盖情况
2. 分析测试函数的覆盖范围

### 3.2 评分计算阶段

#### 步骤 6：逐维度打分

对每个 kernel，按照各维度的分级标准进行打分（1-5 分）。

#### 步骤 7：计算加权总分

```
优先级总分 = 模型热度分 × 0.35
           + 复用度分 × 0.30
           + 核心程度分 × 0.20
           + 测试缺失度分 × 0.05
           + 技术复杂度分 × 0.10
```

#### 步骤 8：优先级分级

| 优先级 | 总分范围 | 行动建议 |
|--------|---------|---------|
| **P0 - 紧急** | ≥4.0 | 立即处理，补充测试和优化 |
| **P1 - 高** | 3.0 - 3.9 | 本迭代内处理 |
| **P2 - 中** | 2.0 - 2.9 | 纳入近期规划 |
| **P3 - 低** | 1.0 - 1.9 | 按需处理 |

### 3.3 结果输出阶段

#### 步骤 9：生成优先级报告

输出 CSV 文件，包含以下列：

| 列名 | 说明 |
|------|------|
| Kernel函数名称 | kernel 函数标识 |
| kernel类型 | vv 或 cv/cube |
| 模型热度得分 | 1-5 |
| 复用度得分 | 1-5 |
| 核心程度得分 | 1-5 |
| 测试缺失度得分 | 1-5 |
| 技术复杂度得分 | 1-5 |
| 优先级总分 | 加权计算结果 |
| 优先级等级 | P0/P1/P2/P3 |
| 使用的模型列表 | 逗号分隔 |
| 共享算子列表 | 逗号分隔 |

## 4. 评分体系

### 4.1 量化指标

| 维度 | 指标来源 | 量化方式 |
|------|---------|---------|
| 模型热度 | 算子-模型映射 + 模型分级表 | 取最高模型级别得分 |
| 复用度 | import 链分析 | 统计共享算子数量 |
| 核心程度 | 函数名 + 调用链分析 | 按位置分类打分 |
| 测试缺失度 | kernel_test_coverage.csv | 按覆盖程度打分 |
| 技术复杂度 | 源码分析 | kernel类型 + 行数 + tl.dot()次数 |

### 4.2 定性指标

| 指标 | 判断方法 | 影响 |
|------|---------|------|
| 仓库独占性 | 该算子是否为 fla 仓库独有实现 | 独占算子的 kernel 优先级上浮 |
| 平台敏感性 | kernel 是否有 NVIDIA/AMD/Intel 平台差异 | 多平台敏感的 kernel 优先级上浮 |
| 近期变更频率 | git log 中该 kernel 文件的近期提交数 | 频繁变更的 kernel 需更多关注 |
| 社区反馈 | GitHub Issues 中与该 kernel 相关的问题数 | 有问题的 kernel 优先级上浮 |

### 4.3 调整规则

1. **独占性加成**：若算子为 fla 仓库独有实现（其他框架无可替代），总分 +0.3
2. **平台敏感性加成**：若 kernel 涉及多平台兼容问题，总分 +0.2
3. **近期变更加成**：若 kernel 文件近 3 个月有 ≥5 次提交，总分 +0.2
4. **社区问题加成**：若 GitHub 有 ≥3 个相关 Issue，总分 +0.3
5. **加成上限**：所有加成累计不超过 +0.5

## 5. 使用案例

### 案例 1：共享核心 Kernel 评估

**Kernel**：`chunk_fwd_h`（位于 `fla/ops/common/chunk_h.py`）

| 维度 | 分析 | 得分 |
|------|------|------|
| 模型热度 | 被 GLA(A级), GSA(B级), RWKV6(B级), MesaNet(C级) 使用 | 4 |
| 复用度 | 5 个算子共享（GLA, SimpleGLA, GSA, RWKV6, MesaNet） | 5 |
| 核心程度 | 前向传播主路径，计算隐藏状态 h | 5 |
| 测试缺失度 | 通过各算子测试间接覆盖，但无直接单元测试 | 4 |
| 技术复杂度 | cv/cube 类型，函数体约 40 行 | 4 |

**总分** = 4×0.35 + 5×0.30 + 5×0.20 + 4×0.05 + 4×0.10 = 1.40 + 1.50 + 1.00 + 0.20 + 0.40 = **4.50**

**优先级**：**P0 - 紧急**

**行动建议**：该 kernel 是仓库中最关键的共享 kernel 之一，影响 5 个算子的前向计算，应立即补充独立的单元测试。

### 案例 2：独占辅助 Kernel 评估

**Kernel**：`rwkv_channel_mixing_pow_and_relu`（位于 `fla/ops/rwkv7/channel_mixing.py`）

| 维度 | 分析 | 得分 |
|------|------|------|
| 模型热度 | 仅被 RWKV7(C级) 使用 | 2 |
| 复用度 | 单一算子独占 | 1 |
| 核心程度 | 前向路径中的融合优化操作 | 3 |
| 测试缺失度 | 有间接测试覆盖 | 3 |
| 技术复杂度 | vv 类型，函数体仅 10 行 | 1 |

**总分** = 2×0.35 + 1×0.30 + 3×0.20 + 3×0.05 + 1×0.10 = 0.70 + 0.30 + 0.60 + 0.15 + 0.10 = **1.85**

**优先级**：**P2 - 中**

**行动建议**：该 kernel 简单且独占，优先级中等，可在 P0/P1 kernel 处理完毕后按需补充测试。

### 案例 3：工业级算子 Kernel 评估

**Kernel**：`chunk_gated_delta_rule_fwd_h`（位于 `fla/ops/common/chunk_delta_h.py`）

| 维度 | 分析 | 得分 |
|------|------|------|
| 模型热度 | 被 GDN(S级), KDA(S级) 使用 | 5 |
| 复用度 | 4 个算子共享（DeltaRule, GatedDeltaRule, KDA, Comba） | 5 |
| 核心程度 | 前向传播主路径，计算状态 h | 5 |
| 测试缺失度 | 通过各算子测试间接覆盖 | 3 |
| 技术复杂度 | cv/cube 类型，函数体约 35 行 | 4 |

**总分** = 5×0.35 + 5×0.30 + 5×0.20 + 3×0.05 + 4×0.10 = 1.75 + 1.50 + 1.00 + 0.15 + 0.40 = **4.80**

**独占性加成**：+0.3（fla 仓库独有的 GDN/KDA 高效实现）

**调整后总分** = 4.80 + 0.30 = **5.10**

**优先级**：**P0 - 紧急**

**行动建议**：该 kernel 被 Qwen3-Next 和 Kimi 两个 S 级产品使用，且为 4 算子共享，是全仓库优先级最高的 kernel 之一，必须确保测试覆盖和性能优化。

## 6. 局限性与注意事项

### 6.1 已知局限性

| 局限性 | 说明 | 缓解策略 |
|--------|------|---------|
| **模型热度主观性** | 模型分级依赖人工判断，可能存在偏差 | 定期根据社区反馈和工业采用情况更新分级 |
| **复用度静态分析** | 仅基于 import 链分析，无法反映运行时实际调用频率 | 结合性能 profiling 数据进行交叉验证 |
| **核心程度简化** | 仅通过函数名和调用链推断，可能遗漏隐含依赖 | 对高分 kernel 进行更深入的调用链分析 |
| **权重固定** | 五个维度权重固定，不同场景可能需要调整 | 提供权重配置接口，允许按场景定制 |
| **定性指标难量化** | 独占性、平台敏感性等指标难以精确量化 | 采用保守的加成策略，避免过度调整 |

### 6.2 使用注意事项

1. **定期更新**：模型热度分级应每季度审查一次，特别是 S/A 级模型的变动
2. **交叉验证**：对 P0 级 kernel 的评分结果，建议由至少两名评估者独立确认
3. **场景适配**：
   - 若目标是**性能优化**，可提高"技术复杂度"权重至 20%，降低"测试缺失度"至 0%
   - 若目标是**测试覆盖**，可提高"测试缺失度"权重至 20%，降低"模型热度"至 20%
   - 若目标是**新平台适配**，可新增"平台兼容性"维度，权重 15%
4. **避免过度依赖**：评分框架是辅助决策工具，不应完全替代工程判断
5. **数据时效性**：CSV 数据可能过时，评分前应确认数据是最新的

### 6.3 扩展方向

1. **自动化评分脚本**：编写 Python 脚本自动完成数据收集和评分计算
2. **CI 集成**：将优先级评估纳入 CI 流程，当新增 kernel 或模型时自动更新评分
3. **可视化看板**：生成交互式看板，支持按维度筛选和排序
